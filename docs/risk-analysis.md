# 校园失物招领平台风险分析

## 选定项目

- 项目名称：校园失物招领平台
- 项目路径：`成员代码/詹冲-校园失物招领平台`
- 本次计划改进功能：志愿者确认失物与拾物匹配接口的权限校验
- 目标接口：`POST /api/volunteer/link`
- 目标文件：`backend/app.py`

## 选择该功能的原因

作业要求本次改动不能只是 README 或前端样式调整，应优先选择涉及身份认证、权限判断、输入处理或数据存取的模块。志愿者匹配确认接口会修改物品状态、写入匹配关系并通知双方用户，属于有明确安全边界的数据写入接口，适合作为本次安全管理实践的单点改进对象。

## 当前逻辑观察

`/api/volunteer/link` 当前流程大致如下：

1. 从请求体读取 `operatorID`、`lostItemID`、`foundItemID`。
2. 根据 `operatorID` 查询用户是否存在。
3. 查询失物和拾物记录。
4. 判断两条记录是否由同一用户发布。
5. 更新两条物品记录的 `ItemStatus` 和 `MatchItemID`。
6. 向失主和拾主创建通知。

## 敏感操作

| 操作 | 涉及数据 | 风险说明 |
| --- | --- | --- |
| 确认匹配 | `Items.ItemStatus`、`Items.MatchItemID` | 会改变物品业务状态，影响后续展示和沟通流程 |
| 创建通知 | `Notifications` | 会向用户发送系统消息，影响用户判断 |
| 操作者识别 | `Users.UserRole` | 若角色校验不足，普通用户可能越权操作 |
| 物品 ID 输入 | `lostItemID`、`foundItemID` | 若不校验类型和状态，可能错误关联记录 |

## 主要安全风险

### 风险一：普通用户越权确认匹配

当前接口只查询 `operatorID` 是否对应存在用户，但“用户存在”不等于“用户有权限”。如果普通用户伪造请求体，可能绕过前端页面限制，直接调用接口完成匹配。

可能影响：

- 普通用户可以把任意失物和拾物关联起来。
- 双方用户收到错误通知。
- 原本未匹配的物品进入“正在联系中”状态，干扰正常流程。

### 风险二：物品类型和状态校验不足

接口名称和参数暗示 `lostItemID` 应对应失物、`foundItemID` 应对应拾物，但当前逻辑需要后续确认是否有强制校验。若缺少校验，攻击者可能传入两条同类型记录或已完成记录，造成状态异常。

可能影响：

- 两条失物或两条拾物被错误关联。
- 已找回、已删除或正在联系中的物品被重复操作。
- 数据状态与业务语义不一致。

### 风险三：缺少必要参数时可能触发异常路径

若请求体为空或缺少关键字段，接口应返回明确的 400，而不是进入数据库逻辑或异常分支。

可能影响：

- 错误响应不稳定。
- 审计时难以区分恶意请求和服务端错误。

## 本次计划整改目标

本次只改进一个功能点，不扩大范围到其他接口：

1. 后端读取请求体时容错处理空 JSON。
2. 缺少 `operatorID`、`lostItemID`、`foundItemID` 时返回 400。
3. `operatorID` 对应用户必须存在。
4. 操作者角色必须是“志愿者”或“管理员”，普通用户返回 403。
5. `lostItemID` 必须对应 `ItemType = Lost`。
6. `foundItemID` 必须对应 `ItemType = Found`。
7. 两条物品都必须处于“未找到”状态才能建立匹配。
8. 继续使用参数化 SQL，不拼接用户输入。

## 不在本次范围内的事项

1. 不引入完整登录态、Session 或 JWT 改造。
2. 不修改数据库表结构。
3. 不修改前端页面样式。
4. 不修改 AI 匹配算法本身。
5. 不处理其他管理员接口的权限问题。
