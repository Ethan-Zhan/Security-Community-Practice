# 整改说明与验证记录

## 整改对象

- 项目：校园失物招领平台
- 接口：`POST /api/volunteer/link`
- 文件：`backend/app.py`
- 函数：`volunteer_link_items`

## 问题是什么

该接口用于志愿者确认失物和拾物匹配，成功后会更新两条物品记录的状态和匹配 ID，并向双方用户发送通知。

整改前的主要风险：

1. 接口根据 `operatorID` 查询用户是否存在，但没有明确限制操作者必须是“志愿者”或“管理员”。
2. 前端页面限制不能作为可信权限边界，普通用户可能伪造请求体直接调用后端接口。
3. 原逻辑没有充分校验 `lostItemID` 和 `foundItemID` 的物品类型与当前状态，可能造成错误匹配或重复匹配。
4. 请求体为空、字段缺失或字段类型异常时，应返回明确业务错误，避免进入数据库更新流程。

## 怎么改

本次整改由 AI 根据 `docs/constraint-doc.md` 中的安全约束和本轮实际对话 Prompt 完成，实际改动如下：

1. 使用 `get_json_body()` 替代 `request.json`，提升空请求体容错能力。
2. 对非对象 JSON 返回 `请求参数格式错误`，状态码 400。
3. 对缺少 `operatorID`、`lostItemID`、`foundItemID` 或空字符串字段返回 `缺少必要参数`，状态码 400。
4. 对字段值为对象或数组的异常输入返回 `请求参数格式错误`，状态码 400。
5. 查询 `operatorID` 的 `UserRole`，无效用户返回 403。
6. 只允许 `UserRole` 为“志愿者”或“管理员”的用户执行匹配确认，普通用户返回 403。
7. 查询物品时增加 `ItemType` 和 `ItemStatus`。
8. 要求 `lostItemID` 对应 `Lost`，`foundItemID` 对应 `Found`，否则返回 400。
9. 要求两个物品都处于“未找到”状态，否则返回 409。
10. 保留原有同一用户不能自匹配限制、通知创建、两条物品更新、`commit()` 和异常 `rollback()`。
