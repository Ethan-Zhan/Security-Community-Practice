# AI 编程约束文档

> 后续每次开启新的 AI 对话前，应完整粘贴本文件。它的作用是把风险分析结论转化成明确的 AI 开发边界，避免 AI 在长对话中遗忘安全约束。

## 背景说明

我们维护的是“校园失物招领平台”，技术栈为 Flask 后端、静态前端页面和 PostgreSQL 数据库。平台包含用户、失物、拾物、通知、聊天、志愿者匹配等功能。

本次作业只允许改进一个功能点：志愿者确认失物和拾物匹配接口。

- 目标接口：`POST /api/volunteer/link`
- 目标文件：`成员代码/詹冲-校园失物招领平台/backend/app.py`
- 当前目标：补充服务端权限校验、参数校验、物品类型校验和物品状态校验

## 任务范围

1. 只修改 `volunteer_link_items` 相关逻辑。
2. 不修改数据库表结构。
3. 不新增第三方依赖。
4. 不修改前端页面和样式。
5. 保持现有成功响应格式兼容前端。
6. 尽量复用项目已有工具函数，例如 `get_json_body()`、`error_response()`、`log_exception()`。

## 必须满足的安全约束

1. 权限校验必须在后端完成，不能只依赖前端隐藏按钮或页面跳转。
2. 请求体为空或字段缺失时，应返回 400。
3. 必须校验 `operatorID` 对应用户是否存在。
4. 操作者 `UserRole` 必须是“志愿者”或“管理员”。
5. 普通用户、无效用户、未登录用户不得执行匹配确认操作。
6. `lostItemID` 必须对应 `ItemType = Lost`。
7. `foundItemID` 必须对应 `ItemType = Found`。
8. 两个物品都必须处于“未找到”状态，才能更新为“正在联系中”。
9. 保留原有“同一用户发布的失物和拾物不能匹配”的限制。
10. 所有 SQL 查询必须继续使用参数化语句，不得拼接客户端输入。
11. 错误响应不能泄露数据库异常、堆栈、连接串、密钥或环境变量。

## 禁止行为

1. 不硬编码账号、密码、Token、数据库连接串或 API Key。
2. 不为了演示方便绕过角色校验。
3. 不把安全校验只写在注释或文档里，必须落实到代码逻辑。
4. 不使用前端 `localStorage` 作为唯一可信身份来源。
5. 不把管理员、志愿者、普通用户统一放行。
6. 不扩大改动到无关模块。
7. 不删除原有通知创建、数据库提交和异常回滚逻辑。

## 期望 AI 输出

AI 后续修改代码时，应输出：

1. 修改了哪些逻辑。
2. 哪些安全约束已落实到代码。
3. 建议运行的验证命令。
4. 是否存在无法验证或需要人工补充测试的部分。
